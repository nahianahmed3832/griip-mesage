# Griip Message — Security model (internal beta)

> **Status:** internal beta. The protection described here was built from vetted library primitives,
> and it has been exercised in the tests listed in `TESTING.md`. **It has not been independently
> reviewed. Do not use it for highly sensitive company information** until the gaps in §4 are closed and a
> review has happened.

## 1. What the relay server can and cannot see

| Data | Server sees it? |
|---|---|
| Message text, attachments, reactions, edits, deletions, pins, read receipts | **No.** These are encrypted on the device before upload (§3). |
| Call audio, video and screen share | **No**, when media E2EE is on, which is the default (§7). Without it, only DTLS-SRTP protects media in transit, so the SFU could read it. |
| Account identity public key, device public keys, usernames, display names | Yes. These form the public directory. |
| Organisation structure: org, branch, department and team names, channel names and topics, memberships, roles | Yes. The server needs them to enforce authorisation. |
| Who sends to which conversation, when, how large each message is, the recipient device list | Yes. This is routing metadata. |
| IP addresses, online status, typing indicators | Yes. |
| Delivery receipts (that a device received a message) | Yes. These are generated by the server. |
| Message history | **No permanent archive.** Encrypted envelopes sit in a temporary queue for at most 7 days and are deleted when the recipient device acknowledges them (`RETENTION.md`). |

Encryption does not hide metadata. A relay operator can see who talks to whom, when, and how much.

## 2. Identity and devices

- **Account identity key:** an Ed25519 key generated on the phone. Its 32-byte seed is the **recovery key** that the
  user can display in *Profile → Security*. The server stores only the public key.
- **Device keys:** each device has its own Ed25519 signing key and its own X25519 encryption key for HPKE.
  A **device certificate** binds them to the account. It is an Ed25519 signature by the identity key over
  `griip-device-cert-v1\n<identityKey>\n<signingKey>\n<encryptionKey>`.
  The server verifies the certificate when a device is registered. Every client verifies it again before encrypting to
  that device or trusting it as a sender.
- **Authentication:** challenge–response. The server issues a single-use nonce that expires after 2 minutes. The device signs
  `griip-auth-v1\n<purpose>\n<nonce>\n<signingKey>`. A session token (256-bit random) is returned, and the server stores only its SHA-256 hash.
  Tokens last 7 days, and the app re-authenticates automatically by signing a fresh challenge. Knowing a username grants
  nothing. Tested in `server/test/auth.test.ts`.
- **Private key storage:** private keys and the session token are sealed with AES-256-GCM using a
  **non-exportable Android Keystore key**, which is hardware-backed where the device supports it. Only that ciphertext is written to
  SharedPreferences. Android backup and device transfer are disabled for keys and the database (`data_extraction_rules.xml`).
- **Linking a new device:** the new phone generates its device keys plus an ephemeral X25519 transfer key and shows a
  10-character code. The existing phone looks up the request, shows the new device's key fingerprint, and on
  approval signs a certificate and seals the identity seed to the transfer key with HPKE. The server only relays
  ciphertext. The new phone verifies that the decrypted seed matches the account identity key before using it.
- **Revocation:** any device of the account can revoke another. The revoked device's sessions and queued envelopes are deleted
  immediately, its WebSocket is closed, and other users are told to refresh their key lists.
- **Recovery:** the recovery key restores the *identity* on a new phone. **History is not recoverable**, because it exists only on
  devices. If the user loses every device and the recovery key, the account cannot be recovered. A server
  administrator cannot impersonate a user: there is no server-side master key, and a new identity key triggers
  "safety number changed" warnings for contacts.

## 3. Message encryption: `griip-envelope-v1`

This is implemented in `android/.../crypto/EnvelopeCrypto.kt` and mirrored byte for byte in `server/test/support/griipClient.ts`.

Per message:
1. `contentKey` is 32 random bytes and `nonce` is 12 random bytes.
2. `header` is `griip-envelope-v1\n<messageId>\n<conversationId>\n<senderUserId>\n<senderDeviceId>\n<sentAt>\n<cls>`.
3. `ciphertext = AES-256-GCM(contentKey, nonce, plaintext=JSON payload, aad=header)`.
4. `signature = Ed25519(senderDeviceKey, header + "\n" + b64(nonce) + "\n" + b64(ciphertext))`.
5. For every recipient device (all active devices of all members, including the sender's own other devices), compute
   `HPKE.Seal(base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM; pkR=deviceEncKey, info="griip-envelope-v1/key", aad=messageId+"\n"+deviceId, pt=contentKey)`.

The server verifies the sender signature and checks that the recipient set equals the current members' active devices.
If not, it returns `409 device_mismatch` and the client refreshes keys. The recipient verifies the signature against a device
key whose certificate chains to the sender's identity key, opens the HPKE wrap, then decrypts and authenticates the content.

**Pinned identities are enforced (T1.2, 2026-10-16).** "Identity key" above means the key **pinned on first contact**,
not whatever the server returns now (`KeyDirectory`; the reference client does the same).
- If the server later presents a different identity key for a contact, that contact is *untrusted*:
  - **sending** to any conversation they're in (DM, group or channel) is paused. Messages show "Paused: a security key changed", and nothing is encrypted to the new devices;
  - **incoming** envelopes from them are **quarantined**: stored locally, acknowledged, and not displayed.
- A banner in the conversation offers *Review*. Accepting pins the exact key whose safety number was shown, not a fresh
  server answer, so a second swap is caught too. It then sends the paused messages and opens the quarantined ones.
- If the server goes back to the pinned key, trust is restored automatically.
- This replaces the audit's finding that pinning was warning-only.

**Libraries:** BouncyCastle 1.79 (HPKE per RFC 9180, Ed25519 per RFC 8032), platform JCA AES-GCM on Android, and
`@hpke/core` 1.9 plus Node `crypto` in the test client. **No primitive is implemented by us.** The *composition* is ours and
has not been reviewed. It sits behind the replaceable `MessageCrypto` interface, so that Signal Protocol or MLS can be swapped in later.

Interop between the Kotlin and Node implementations was verified on a physical phone in both directions (`TESTING.md` §3).

## 4. Known gaps (read this)

- **No forward secrecy and no post-compromise security.** Content keys are wrapped to long-term device keys. If a device's
  X25519 private key is stolen, every message ever wrapped to that device can be decrypted, provided the attacker also captured
  the ciphertext (the relay keeps it for at most 7 days). Signal's Double Ratchet and MLS fix this. Neither was integrated in
  this beta (`DECISIONS.md` D-04).
- **Trust on first use.** The first identity key seen for a user is pinned, so a key substituted *before* first contact
  isn't detected. Users can compare safety numbers in person (*Contact → Safety number*) and mark contacts as verified.
  A later change pauses messaging with that contact until the user accepts the new key (§3).
  - A legitimate re-registration (a lost phone without the recovery key) therefore needs every contact to accept the new key.
  - In a large channel, one member's change pauses sending there until the user accepts it, because the server requires
    every member device in the recipient set.
- **Group membership is server-asserted.** The server decides who is a member of a channel. A malicious server could add a device
  and receive future messages. Clients encrypt only to devices certified by members' identity keys, but they don't
  independently verify the membership list. Fixing this needs MLS-style signed group state.
- **Deletion and editing are cooperative.** A modified client can ignore delete or edit requests.
- **Read receipts and typing** are visible to conversation members. Typing and online status are visible to the server.
- **Session tokens** are bearer tokens. With the debug build's `http://` mode (testing only) they are exposed on the network.
  Production uses TLS (`https://msg.griipbuddy.cloud`).

## 5. Safety numbers

The fingerprint of an identity key is `SHA-256(identityKey)`, split into six 5-byte chunks, each taken mod 100000 and zero-padded to
5 digits. The safety number for a pair of users is the two fingerprints sorted and joined with a newline, so both phones show the same value.

## 6. Local storage

- The Room database is encrypted with **SQLCipher 4.12** (AES-256). Its 256-bit random passphrase is sealed by the Keystore key.
- Downloaded and sent attachments are written to app-private storage (`filesDir/attachments`). They rely on Android
  file-based encryption, not SQLCipher. "Sign out & erase" first revokes the device on the server (T1.9), so contacts stop encrypting to it, then deletes the keys, the database and the attachments. If the revocation can't be confirmed, the user is told and decides whether to erase anyway.
- Plaintext of unsent messages lives only in the encrypted database's outbox table.
- **Notifications (T4.4):** message notifications show decrypted text and are private on the lock screen ("New message" only).
  The few recent lines a notification shows are held in memory, never on disk. *Reply* and *Mark as read* require the phone to be
  unlocked, go only to the app's own non-exported receiver, and *Reply* is offered only where the user may post. "Sign out & erase"
  now also removes message notifications, so decrypted text doesn't stay in the shade.

## 6b. Scanned QR codes

- The in-app scanner (T4.2) decodes frames on the phone and accepts **only Griip invite codes** (`InviteCodes.fromScan`). It never
  opens a URL from a QR code, and `griip://invite` deep links pass through the same parser. A scanned code only fills the join form;
  joining still needs the invite preview and an explicit tap.

## 7. Call media

- Calls use LiveKit 1.13.10 (self-hosted SFU) with the official LiveKit Android SDK 2.29.0.
- **Media E2EE:** the caller generates a random 256-bit key per call and sends it to the conversation's devices
  **inside a `griip-envelope-v1` encrypted control message** (`call_invite`). It is never sent through the call API, a URL or a token.
  Every participant sets it as the LiveKit shared key (AES-GCM frame encryption with PBKDF2 key derivation, the SDK default).
  If E2EE is enabled and the key hasn't arrived after about 10 s, **the app refuses to join instead of downgrading**.
  The first key received for a call is kept, so a later `call_invite` for the same call can't replace it.
  **Since T5.2 (2026-10-16), a key is accepted only from the call's creator**, in the call's own conversation: the app looks up the
  call (`GET /v1/calls/:id`) and compares `createdBy` with the envelope's signed sender. Keys from other members are ignored and logged.
  If the lookup fails for a reason other than 404, the queue item is redelivered and checked again; it is never accepted unchecked.
- **Late joiners (T5.3):** a device that has no key for a call it is joining sends a `call_key_request` control in the call's
  conversation. Only the call's creator answers, re-sending the same key inside a `call_invite` to the conversation's current
  member devices, the same audience the server admits to the call. Requests and answers are paced (1.5 s grace, then at most
  every 5 s per call), and ended calls are never answered.
- **Verified:** on the production SFU, a participant with the correct key decoded video and audio, and a participant with a wrong key
  decoded nothing (`TESTING.md` §4).
- **Gaps:** the key is not rotated when participants leave or join. A removed member who still has the key could decrypt
  media *if* they could also obtain the SFU-forwarded packets.
  **Removal from calls (T1.3, implemented 2026-10-16, not yet deployed):**
  - When someone loses membership of a conversation (removed, leaves, removed from the org, branch or team, or demoted
    to Guest), the server removes all their devices from that conversation's live LiveKit room. It also does this when one of
    their devices is revoked or their account is disabled. The person's devices are told the call ended (`endReason: "removed"`).
  - `join` and `connected` return 404 for them.
  - Their LiveKit token can stay valid for up to 10 minutes, and LiveKit can't revoke it. A rejoin with that token is ejected as soon as
    LiveKit's webhook arrives, and in any case by the 60 s reconciliation job, which also repairs removals LiveKit missed while unreachable.
  - Until deployed, production still has the audit's finding (probe P3).
  The key is per call and is deleted from the device 24 h after the call ends.
- LiveKit tokens are JWTs scoped to one room, valid for 10 minutes, and issued only to conversation members.

## 8. Server hardening

- Every route validates input with zod. Body limits apply (256 KiB default, 2 MiB for messages, 25 MiB for attachments).
- **Registration is invite-only by default (T1.6).** A new account needs either a registration invite or a valid org invite.
  - Registration invites are issued only by the operator CLI.
  - Org invites are minted only by authenticated org managers.
  - Codes are 60-bit random and stored as SHA-256 hashes. Uses and expiry are bounded and enforced inside the registration transaction.
  - Residual risk: anyone who can create an org can invite people into it, and so let them register.
- **Route audit (2026-10-16):** every route requires a session except registration, login, challenge, device-pairing bootstrap and the
  signature-checked LiveKit webhook. Each resource route checks membership or role in `authz.ts`. Two deliberate openings to revisit:
  - anyone can add any user to a new group without consent;
  - device public keys can be looked up for any user id. They are public key material by design, but they reveal how many devices a user has.
- **Presence privacy (T1.7):** online state and last-seen are shown only to the person, to anyone sharing a conversation
  with them, and to non-guest members of a shared org (`Authz.canSeePresence`). Knowing a username or id reveals nothing;
  realtime presence events go only to DM and group peers.
- **Upload quotas (T1.6):**
  - Attachments stream to disk; nothing buffers a whole file in memory.
  - Limits: per-user daily and stored bytes, a server-wide byte cap (`507`), and per-user and global concurrent uploads and in-flight bytes.
  - Partial files from interrupted uploads are deleted, and stale ones are removed at startup.
  - Containers have CPU, memory and process limits.
  Rate limits are global per device or IP, with tighter limits on auth and invite endpoints.
- Authorisation is enforced on the server for every resource (`server/src/authz.ts`). Non-members get `404` to avoid
  leaking existence. Tested with direct API calls in `server/test/orgs.test.ts`.
- All IDs are 128-bit random. Invite codes are 60-bit random, stored hashed and rate-limited. Attachment downloads require
  membership of the conversation they were uploaded to.
- Logs never contain request bodies, Authorization headers or message content.
- There is no admin HTTP surface. Operator commands run through `docker compose exec api node dist/admin.js`.
- The API and LiveKit signalling bind to `127.0.0.1` behind the host's nginx TLS. Only LiveKit's media ports (7881/tcp, 7882/udp) are public.
